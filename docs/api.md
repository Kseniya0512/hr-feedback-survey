# Контракт серверного API

Приложение содержит готовый клиентский адаптер в `js/storage.js`. Этот документ — контракт для корпоративного backend, **не работающий сервер**. Разместите статику и API на одном HTTPS-origin. HTTP допускается адаптером только для localhost/127.0.0.1/::1 при разработке.

Адрес в настройках — базовый, без параметров, фрагмента и учётных данных, например `https://survey.company.ru/api`. Запросы используют `credentials: include`, `Accept: application/json`, тайм-аут 15 секунд. API не должен перенаправлять API-запросы на HTML-страницу SSO: для отсутствующей сессии возвращайте JSON и HTTP 401/403. Вход выполняется отдельно через корпоративный сервис.

## Запись ответа

`POST /responses`, `Content-Type: application/json`, `Idempotency-Key: <id>`.

```json
{
  "id": "05b6ca97-4737-4892-8cfa-94bfc6512367",
  "survey": "participant",
  "createdAt": "2026-11-05T10:00:00.000Z",
  "initiative": "Новый процесс адаптации",
  "department": "HR",
  "answers": {
    "p1": 4, "p2": 5, "p3": 4,
    "p4": 4, "p5": 3, "p6": "mostly",
    "p7": 4, "p8": 5, "p9": "not_contacted",
    "p10": 4, "p11": "mostly", "p12": ["training"],
    "p13": "Были понятные инструкции",
    "p14": "Добавить практику"
  }
}
```

- `survey`: только `implementer` или `participant`.
- `id`: ASCII буквы/цифры/underscore/hyphen, 1–100 символов; приложение генерирует UUID.
- `createdAt`: время клиента ISO 8601. Для аудита сервер должен отдельно записывать собственное время получения.
- `initiative`, `department`: строки до 200 символов, допускаются пустые.
- `answers`: только известные ключи своей аудитории. Точная схема и варианты — `js/surveys.js`; чистая проверка — `HRCore.validateRecord` в `js/core.js` (CommonJS-совместима). Шкалы передаются числами, специальные ответы строками, множественный выбор массивом уникальных строк. «Другое» — вариант без обязательного дополнительного текста; детали можно указать в открытых комментариях.
- Открытые ответы необязательны, до 5000 символов. Незаполненные могут отсутствовать.
- Для **старой команды v1**: `i14` отсутствует, если `i13` содержит только `none`; `i3`/`i13` исключают остальные при `none`. Для участников `p12=none` по-прежнему исключает другие варианты.

### Новая анкета команды (questionnaireVersion: 2)

Формат участников выше не меняется. У implementer обязательна явная версия 2; отсутствие версии означает **старую** анкету. Не определяйте версию по совпадающим ключам `i1…i20`.

Новые необязательные метаданные: `initiativeId` — строка до 100 символов, пустая допустима. Поле нужно для отдельной агрегации инициатив. Само имя `initiative` не является идентификатором. Версия JSON-контейнера списка/экспорта по-прежнему 1.

Минимальный полный пример на стадии подготовки:

```json
{
  "id":"03d16795-1b28-4cdc-a2b8-722984f3257b",
  "survey":"implementer",
  "questionnaireVersion":2,
  "initiativeId":"HR-001",
  "initiative":"Новый процесс адаптации",
  "department":"HR",
  "createdAt":"2026-11-09T10:00:00.000Z",
  "answers":{
    "i0_1":["initiator"],"i0_2":"preparation",
    "i1":4,"i2":5,"i3":["none"],
    "i4":{"sponsor":4,"initiator":5,"team":3,"cei":"na","leaders":"na","champions":"na"},
    "i5":["not_yet"],"i6":["none"],
    "i8":"same","i10":4,"i11":"too_early",
    "i12":["none"],"i13":"support",
    "i18":["goal"],"i19":["simplify"],"i20":"Добавить примеры"
  }
}
```

- `i0_1`: несколько ролей; `i0_2`: preparation/start/main/complete/implemented.
- `i4`: объект **ровно** из sponsor, initiator, team, cei, leaders, champions; каждая строка — число 1–5 или `na`.
- `i3Other`: необязательный текст до 5000 символов, только если в `i3` выбран `other`.
- `i7`: один вариант из реальных проблем `i6` (без none/not_yet), обязателен только при наличии проблем.
- `i9`: непустой массив, обязателен только если `i8=more` или `much_more`.
- `i14`/`i15`/`i16`: применимы на всех стадиях, кроме preparation.
- `iLaunched`: необязательная булева отметка фактического запуска новых правил. Применима после preparation; только при true применим `i17`. Стадия implemented сама по себе не подменяет явную отметку пользователя.
- `i19`: от одного до трёх уникальных вариантов.
- `i20`: необязательный текст до 5000 символов.
- Исключающие варианты определены в `exclusive` схемы (включая none/not_yet/too_early/unsure в своих вопросах). Их нельзя совмещать с другими.

Серверу нужно повторять version-aware проверку `validateRecord`; перед записью можно использовать `pruneAnswers(survey, answers, versionOf(record))`, чтобы исключить неприменимые ответы. Клиент при отправке/экспорте удаляет скрытые ответы. При чтении старого импорта валидные скрытые ответы могут сохраняться для совместимости, но не участвуют в показателях. `HRCore.exportRecords` создаёт очищенную копию без изменения хранимых записей. Импорт/экспорт обязан сохранять `questionnaireVersion`, `initiativeId`, матрицу и дополнительный текст.

Ответ: HTTP 201 (или 200 при повторной отправке), JSON с **тем же** ID:

```json
{"id":"05b6ca97-4737-4892-8cfa-94bfc6512367"}
```

Не подтверждайте запись до её сохранения в транзакции. Уникальный индекс по ID и серверная идемпотентность обязательны: при сетевом сбое клиент повторяет запрос с тем же ID и ключом. Дублирование того же содержимого возвращает тот же ID; одинаковый ключ с другим содержимым — HTTP 409, без изменения исходной записи. Идемпотентность привязывается к области опроса/организации, а не доверенным клиентским заголовкам. Ошибки 400/422, 401/403, 409, 429, 5xx не считаются подтверждением.

## Сессия администратора

`GET /session`

```json
{"role":"admin"}
```

Сервер получает роль из проверенной корпоративной сессии/SSO и возвращает 401/403 без прав. Любая другая роль не разрешает клиенту запрашивать результаты. Данный предварительный запрос — удобство интерфейса; защита данных должна находиться на самом endpoint списка.

## Список результатов

`GET /responses`, только для серверного администратора:

```json
{"version":1,"responses":[]}
```

Каждая запись соответствует схеме POST. Клиент проверяет полученные данные и затем рассчитывает аналитику и экспортирует текущую выборку локально. Текущий контракт получает всю выборку за один запрос; для больших объёмов потребуется отдельная доработка пагинации/серверной агрегации. Доступ к результатам и экспорту, если появится серверный endpoint экспорта, должен иметь одинаковые права и корпоративную область видимости.

## Безопасность и эксплуатация backend

1. Реальная корпоративная авторизация, серверная проверка admin на каждом запросе данных. Никогда не отдавайте список, надеясь скрыть его кнопкой в UI.
2. HTTPS, session cookies `HttpOnly`, `Secure`, подходящий `SameSite`, ограниченная область cookie. Для рекомендуемого same-origin размещения не нужен CORS.
3. CSRF-защита POST: проверка точного `Origin`/`Sec-Fetch-Site`, требование `application/json`, cookie SameSite и отклонение запросов с недоверенных origins. Если корпоративная платформа требует CSRF-токен, добавьте его выдачу и передачу в адаптер, не помещая секреты в localStorage.
4. При раздельных origins настройте точный allowlist CORS, `Access-Control-Allow-Credentials: true`, `Vary: Origin`, методы GET/POST/OPTIONS и заголовки Content-Type/Idempotency-Key. Не используйте `Access-Control-Allow-Origin: *` с credentials. Не разрешайте origin `null` для production file://. Сторонние cookie могут быть заблокированы; предпочтителен один origin.
5. Повторная серверная валидация тела, лимит размера запроса, rate limit, уникальный ID, транзакции, экранирование при отображении, журналирование без содержимого персональных комментариев, разграничение по корпоративной области.
6. Согласованные с организацией сроки хранения/удаления, резервное копирование и уведомление участников об обработке. Отсутствие поля имени не доказывает анонимность: SSO, логи и текст комментариев могут идентифицировать автора.
7. Ограничьте чтение данных БД сервером; не открывайте корпоративное хранилище напрямую из браузера с постоянным API-ключом. Токены и секреты не входят в клиентскую конфигурацию.

## Приёмка реального подключения

Проверьте последовательно: POST → запись в БД → повтор с тем же ID не создаёт дубль → обычный сотрудник получает 403 на GET /responses → администратор получает список → корректность фильтров и экспорта → истечение сессии → сетевой сбой/тайм-аут с сохранением черновика → повторная отправка → отклонение недоверенного Origin. Наличие адаптера в статическом проекте само по себе не означает, что сервер подключён.
